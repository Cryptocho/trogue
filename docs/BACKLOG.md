### A3. 修复模板 `template/tools/gen_font.py`（反馈 C2 / F1）

- **验收**：对真实 `.ttc` + 字符集文件跑通，产出 PNG + metrics；`--index 2` 生效。

### A4. 模板 IPC handler 输入校验规范 + 工具冒烟（反馈 C1 / §D-1）

- **问题**：引擎把未校验的 JSON 直接交给 game handler **是正确的边界**（引擎不识
  命令语义），但模板只在 `move` 命令示范了类型校验；探针在其余 13 个命令漏检，
  导致试玩期 3 次静默崩溃（nlohmann `.get<int>()` 对类型不符抛异常）。这是**模板
  纪律缺口**，不是引擎缺口。
- **位置**：模板 `AGENTS.md`；模板 `tools/ipc_smoke.py`。
- **动作**：
  ① 模板 `AGENTS.md` 加硬性检查项：「IPC 命令参数是**不可信输入**——每个字段显式
  校验类型与范围，错误统一走错误包络；禁止裸 `.get<T>()`。冒烟脚本必须覆盖每条

  ② 模板 `ipc_smoke.py` 为每条命令补一条负向路径断言（类型错/缺字段 → 错误包络，

  所有派生项目的第一次体验（A3 正是该纪律缺失的产物）。
- **验收**：模板负向路径断言全过；对模板工具跑一遍冒烟有记录。

## B. 评估队列（需先定设计，再走门禁）

### B1. `tg::Random` 状态可观测性（反馈 C3 / F2）——**已定：只做 T1**

- 唯一的引擎候选缺口（其余为模板/文档）。
- **决定（2026-09-14）**：只做 **T1**——`tg::Random` 增加**只读原始抽取计数**
  `draws()`。不暴露状态字、不做序列化。
- **精确语义（必须钉死，否则 T1 无效）**：`draws()` 计的是**原始 `next_u64`
  的调用次数**（状态推进次数，含 `next_int`/`next_double`/`next_bool`/`pick`/
  `shuffle` 内部消耗的那些），**不是高层 API 调用次数**。因为 xoshiro256** 的
  状态每次 `next_u64` 推进一次，`(seed, draws)` 才能唯一确定流位置；若计成 API
  调用数，拒绝采样（`next_int`）与 `next_bool` 的边界短路会立刻让它失真。
  类型 `uint64_t`、`noexcept`、`const`、**只读**（不提供 set——那会滑向 T3 并
  重新引入全零不动点问题）。拷贝语义自然延伸：拷贝 = 复制状态与计数，与
  `random.hpp` 既有「拷贝 = 存档某刻随机状态」一致。
- **它解决什么**：把「seed + 重放」从**静默错位**变成**可验证**——探针的
  `seed + rng_calls` 绕法原本无法验证（拒绝采样消耗可变、`next_bool` 短路零消耗）。
- **它不解决什么（勿高估）**：**不提供 O(1) 跨进程恢复**。F2 的原始诉求（跨进程
  存档/回放）仍待第二消费方。测试价值亦为次要（黄金序列已冻结输出，`draws()`
  只抓「消耗数变但前几个输出恰好相同」的罕见回归）。
- **T2/T3 判定：不是「延后」，而是「不需要」**（2026-09-14 收紧）：
  - 关键认识：**「O(1) 恢复」本身不是真需求**。真实需求是「恢复到流中某一点」，
    而 `(seed, draws)` + 重放**已经满足**它——重放成本 O(draws) 在存档/回放场景
    完全可接受（存档点稀疏、重放是纯算术、无 I/O）。O(1) 只是实现偏好，不是需求。
  - 因此 T2（带版本 blob）与 T3（4×u64 裸状态字）**均不采纳**，非「等第二消费方」：
    - T3 反对理由：把「改算法」从响亮失败（黄金序列失效）变成**存档静默错位**
      （旧存档被新引擎读出看似合理但错误的序列），且把内部布局冻结为永久契约；
    - T2 反对理由：为不存在的需求引入格式版本、不可信输入校验（全零不动点）、
      迁移路径等一整套复杂度。
  - **诚实边界**：这是**判断**，不是证明——若将来出现「必须不重放就恢复」的硬需求
    （如每帧快照、或重放成本真的成为瓶颈），T2 仍可叠加（T1 不封死它）。届时按
    新证据重议，而非按「O(1) 更好」的直觉。
- **触发条件（已弱化）**：仅当出现「无法承受重放成本」的具体证据（非「想要 O(1)」
  这类实现偏好）时，才重议 T2。T1 本身不设触发条件——它已定，待实施。

### B2. `Ipc::publish` 返回送达情况（反馈 C9）——**倾向不做**

- 当前「慢消费者/超限即断开、无出站队列」是**刻意设计的自愈模型**。要「统计丢弃」
  需引入出站队列，与既有设计冲突；返回瞬时写状态信息量极低。除非出现第二个消费
  方提出具体可观测需求，否则维持现状（可考虑仅文档说明丢弃不可观测）。

### B3. 字体管线升格（反馈 C4）——**部分采纳**

- **采纳**：修工具 + 文档澄清（即 A3）。
- **不采纳**：「从可选参考升为一等标准模块」——与模板「不预设管线/不引导」原则
  冲突，且反馈自身 §D-5 亦担忧示范引力。替代方向：让 **opt-in 更顺**（CMake 选项
  或更清晰的一步接入说明），而非默认升格。

### B4. 模板 `step_frames` 上限 3600（反馈 C8）

- 模板自有常量（`template/game/src/main.cpp` 的 `[1,3600]`），非引擎限制。塔防
  Boss 波 >60s 需一次推进更多步。动作二选一：放宽上限，或文档说明分块调用。
- 影响面小，可并入下一轮模板改动。
